Five hosts are managed by Ansible from dgx-1 (`hosts/inventory.yml`). The MacBook Air is out of scope. This page is
the summary; each host has its own page.

## Inventory

| Inventory name | Groups (`hosts/inventory.yml`) | OS | Ansible user | k3s role |
|---|---|---|---|---|
| dgx-1 | `sparks`, `k3s_servers`, `bus` | Ubuntu 24.04.5, kernel 7.0.0-1025-nvidia | `nikghodki-dgx` (local connection) | server + etcd |
| dgx-2 | `sparks`, `k3s_servers`, `k3s_init`, `observe` | Ubuntu 24.04.5 | `nikghodki-dgx-2` | server + etcd, started the cluster |
| jetson | `jetson_group`, `k3s_servers` | Ubuntu 24.04.4 (JetPack 7.2.1, L4T R39.2.1), kernel 6.8.12-tegra | `nikjetson` | etcd-only member + kubelet, tainted |
| omarchy | `agent_nodes`, `k3s_agents`, `always_on`, `alerting` | Omarchy (Arch), kernel 7.2.15-omarchy | `nikghodki` | agent |
| pi | `edge` | Debian 13 trixie (Raspberry Pi OS) | `nikghodki-raspberry-1` | none |

Group meaning: `bus` = where NATS and the Fleet stack run; `observe` = where the observe, console, jobs, ml and backup
stacks run; `alerting` = where Gatus, ntfy and Homepage run; `edge` = robot devices.

## Access from the admin laptop

Nothing is written or run on the laptop. It only holds SSH tunnels into the fleet:

| Target | Command on the laptop | Notes |
|---|---|---|
| dgx-1 | `ssh -p 2244 nikghodki-dgx@localhost` | The control node. Work happens here. |
| Jetson | `ssh -p 2245 nikjetson@localhost` | |
| Pi | `ssh -p 2248 nikghodki-raspberry-1@localhost` | Relayed through the Jetson (unverified how the tunnel is built) |
| dgx-2 | from dgx-1: `ssh nikghodki-dgx-2@192.168.86.36` | LAN |
| Dell | from dgx-1: `ssh nikghodki@192.168.86.49` | LAN; `docker` needs `sudo` |

How the laptop-side tunnels (ports 2244, 2245, 2248) are set up is not in the repo (unverified). When a command runs
over SSH inside a heredoc, use `ssh -n`, or ssh eats the rest of the heredoc as its stdin.

## Memory budget

| Host | Total | Budget rule | Measured 2026-11-15 |
|---|---|---|---|
| dgx-1 | 121 GiB unified (CPU + GPU) | Keep ≥ 8 GiB free (P2.7, not enforced by DGXMM yet). Services use about 8–10 GiB (decision 0009). AIBOM capped at 6 GiB. | 8 GiB used, 113 GiB available, no engine loaded |
| dgx-2 | 121 GiB unified | Reserve 15–23 GiB for services (P2.7). Sim jobs ≤ 16 GiB cgroup and JAX ≤ 15% of memory. AIBOM capped at 6 GiB. | 6 GiB used, 115 GiB available |
| Jetson | 7.4 GiB | About 3.4 GiB available with everything running; kubelet reserves 4 GiB + 768 MiB, pods get about 2.3 GiB, eviction under 300 MiB | 3.4 GiB available |
| Dell | 7.7 GiB | One small workload at a time; 2 cores are the real limit | 5.4 GiB available |
| Pi | 3.7 GiB | About 1 GiB without vision | 3.1 GiB available |

A GPU job on a Spark can use all of the unified memory and take the host's services down with it. That happened on
2026-11-15 (see [GPU OOM incident](../operations/incident-gpu-oom.mdx)).
